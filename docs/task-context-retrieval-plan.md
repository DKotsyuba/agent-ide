# Разведка по задаче: технический план

Статус: реализация в изолированной рабочей ветке; окончательная готовность подтверждается отдельными результатами проверок. Согласованная основа: builder → широкий поиск с embeddings → точечный отбор Jev → пакет исходников. Эмбеддинги сначала через API, архитектура допускает локальный сервис. Jev — существующий маршрут OpenRouter. Реальные обращения, установка моделей, выпуск и изменение рабочего конфига этим документом не выполняются.

## 1. Результат и границы

Агент передаёт точный текст задачи и бюджет контекста, IDE возвращает проверяемый пакет исходников, связанных контрактов и тестов. Поиск сохраняет полный каталог проекта; исключение из текущей выдачи не исключает объект из последующих расширений. Нужные файлы не объявляются единственно возможными файлами правки.

Первая версия: один репозиторий/рабочая копия на запрос; чтение и индексирование; без записи исходников и автоматического запуска диагностических команд. Для неопределённой задачи допускается needs_evidence с конкретно указанным пробелом. Инструкции проекта, версии файлов, доступ и отмена сохраняют существующие правила IDE. Никакого анализа домашнего каталога или соседних проектов.

## 2. Что уже есть и что отсутствует

- project/structure.rs: ограниченный обход, структурированное дерево, заголовки, текстовый skeleton, импорты, Git и лимиты. Default max_depth=3/max_nodes=2000 и ограничения чтения НЕ означают полного индекса проекта. Ограничения представления нельзя использовать как неявный предел покрытия индекса.
- project/token_estimate.rs: приблизительный счётчик символы/коэффициент; пригоден для предварительного объёма, не для гарантии лимита конкретной модели.
- intelligence/names.rs и assistance/links.rs: индекс имён и проверяемые связи в поддерживаемых областях. Это НЕ полный межъязыковой граф вызовов.
- assistance/support/client.rs: настраиваемый маршрут Jev, HTTPS, приватный ключ, ограничения транспорта, проверка ответов, usage. Пилотные вопросы и lifecycle не являются универсальным поисковым сервисом.
- assistance/support/packet.rs и текущая доставка: проверка источников, версии/окна и приватные подготовленные пакеты. Старые лимиты состояния 8 KiB и артефакта 24 KiB относятся к прежнему пилоту; новая разведка получает отдельный явный бюджет, без скрытого повышения старого лимита.

## 3. Границы компонентов

Планируемый внутренний модуль project/context/ без нового crate на первом шаге:

| Компонент | Ответственность | Не отвечает за |
|---|---|---|
| builder / source records | авторизованный сбор фактов и исходных диапазонов | выбор по смыслу, HTTP, решения Jev |
| index.rs | поколения индекса, локальный cache, изменение/удаление файлов | задача агента и ранжирование |
| embedding.rs | embed_documents/embed_query, API/local adapters, проверка векторов | окончательное исключение файлов |
| retrieve.rs | точный и семантический поиск, объединение результатов, расширение связей | выдуманные связи и код |
| jev.rs | типизированная оценка предложенных кандидатов и выбор следующего чтения | генерация путей, shell-команд, правок |
| packet.rs | раскрытие выбранного кода, бюджет, provenance, свежесть | выдача private reads за доставку агенту |
| mod.rs | orchestration, request/cancel, этапы и общий budget | отдельный постоянный daemon или framework |

Границы — обязанности, не требование немедленно создать все файлы. Маленькие части остаются функциями, пока отдельный файл не помогает.

## 4. Расширение builder

Перед каждым расширением сообщать владельцу изменение и назначение.

1. Разделить обнаружение путей, извлечение source facts и render. Сохранить старые build_structure/render_tree и поведение CLI.
2. Добавить структурированный экспорт объявлений из уже полученного Outline: имя, вид, квалифицированное имя, сигнатура, родитель, исходные диапазоны и комментарий. Не разбирать обратно текст skeleton и не запускать повторный parser ради индекса.
3. Добавить идентичность рабочей копии, относительный путь, digest содержимого, версию extractor и статус полноты. File ID привязан к root+path; rename не обещает сохранения идентичности. Content hash позволяет переиспользовать вычисления при переносе одинаковых байтов. Symbol ID включает file ID и разрешённый extractor идентификатор; неоднозначность/перегрузки отмечаются.
4. Обнаружение всего разрешённого дерева сделать возобновляемым с явным coverage. Parse/read budgets отдельные; collapsed, unavailable, omitted и indexed различаются. Неподдерживаемый язык остаётся доступен для path/text поиска.
5. Выборочное раскрытие source windows по ID и версии. Малые файлы целиком, большие — законченные объявления с нужным окружением; не случайные префиксы по 1536 байт.

Не делать README обязательным. Докстринг привязан к своему объявлению; ссылки документации разрешаются в реальные пути/символы. Соседство каталога и совпадение слов — только weak evidence. Автоматические описания ответственности не подменяют факты.

## 5. Контракты данных

- ProjectSnapshot: root identity, generation, extractor versions, coverage, exclusions, unavailable reasons.
- FileRecord: file_id, relative_path, content_hash, language, size, header, imports, symbol refs, extraction status.
- SymbolRecord: symbol_id, file_id, source range, kind, qualified_name, signature, doc, parent.
- LinkRecord: from/to, relation, evidence source (resolved reference/import/test coverage/name convention), confidence class и source versions. Лексическое совпадение не называется подтверждённым вызовом.
- ChunkRecord: chunk_id, source refs, exact content digest, embedding-template version, role, input text. Данные renderer decoration не входят в embedding.
- Candidate: source refs, rank per search channel, match evidence, role hypothesis, expansion frontier.
- JevDecision: question IDs, candidate IDs, typed values, actual model identity, usage, status. ID однозначно связан с показанной карточкой в state.
- ContextBundle: task digest, snapshot, primary/support/tests sections, exact source windows, inclusion reasons, uncovered/omitted areas, token accounting, status complete/partial/needs_evidence.

Stable IDs используются внутри одного актуального snapshot; диапазоны и content hash проверяются повторно перед чтением/выдачей.

## 6. Индекс и embeddings

По решению владельца данные этой разведки хранятся в `.agent-ide/` в корне проекта: SQLite-индекс, embedding-векторы, метаданные поколений и приватные журналы. При первой инициализации IDE добавляет корневое правило `/.agent-ide/` в `.gitignore`, сохраняя существующие записи и не создавая дублей. Каждая рабочая копия использует собственный каталог; переход на соседнюю копию не переиспользует её индекс неявно. Уже отслеживаемые Git файлы автоматически не удаляются из индекса Git: правило ignore не прекращает их отслеживание, такая ситуация явно сообщается. Собственный каталог исключается из обхода, чтения контекста и embedding даже при отключённом respect_gitignore. При недоступной записи инициализация сообщает причину, без скрытого переноса данных в другое место. Каталог данных должен быть закрыт для других пользователей; секреты провайдеров в него автоматически не копируются. Существующее глобальное состояние демона этим решением не мигрируется. Использовать имеющийся SQLite; индекс не смешивать с таблицами operation receipts. Наличие FTS5 проверить в реально собираемой rusqlite, не предполагать. Точный поиск на первом шаге может использовать существующий код поиска, без новой библиотеки.

Единицы embedding: карточка файла и осмысленное объявление/группа небольших связанных объявлений. Вход: relative path + язык + сигнатура + документация + ограниченный реальный код. Большие объявления делятся по структурным границам с сохранением контекста родителя. Заголовки дерева, Git-счётчики и декоративные линии не индексируются в вектор.

EmbeddingClient имеет отдельные embed_documents и embed_query: одинаковая модель/пространство, но provider-specific task prefixes/input_type могут различаться. Config: backend api/local, protocol, base_url/path, model/revision, dimensions, normalization, batch/request limits, concurrency, timeout, credential_file, egress policy и budget.

Первым подключить API adapter. OpenRouter допускает embeddings endpoint, но модель выбирается после проверки её multilingual RU-task/English-code качества, размеров, лимитов и стоимости. Смена URL/model — конфиг и новая сессия, не пересборка. Локальный вариант сначала через явно подготовленный совместимый сервис; без встраивания inference runtime и автоматического скачивания модели. Общий интерфейс и fixture-контракт делаются сразу, реальное локальное provisioning — отдельный последующий шаг.

Проверять количество/порядок ответов, индексы, model identity, dimension, finite values, zero norms. Нельзя смешивать пространства разных моделей/версий/размерностей. Cache key включает content, шаблон, роль query/document, модель/версию/размерность/нормализацию и область доступа. Изменение настроек создаёт новое поколение, а не смешивает старые векторы.

На пилоте — точный поиск по векторным расстояниям для ограниченного измеренного объёма. Нет отдельного vector DB/ANN engine до измерения RAM/latency. Если точный поиск не укладывается в целевой budget, отдельно выбрать встроенный ANN по текущей library-first процедуре.

Обновление: дешёвое обнаружение изменений → сравнение content hashes → извлечение изменённых записей → embeddings только изменённых chunks → атомарная публикация поколения. Delete удаляет привязки; незавершённый индекс не показывается как полный. Старые результаты всегда сверяются с рабочими байтами. Background work ограничено, отменяется и выполняется вне последовательного worker/locks.

## 7. Поиск под задачу

1. Сохранить точный текст задачи, её digest и доступный scope; не заменять задачу кратким предположением.
2. Получить кандидатов из точного поиска путей/символов/строк ошибок и независимого embedding поиска. Прямые совпадения не отбрасываются из-за низкого semantic score.
3. Объединить списки через ранги (например, RRF), не складывая несопоставимые численные scores. Ограничить доминирование одного большого файла, сохранить разнообразие областей. Размеры shortlist/budgets подобрать offline и зафиксировать перед сравнением.
4. Добавить имеющиеся прямые зависимости, потребителей контрактов и связанные тесты. Помечать подтверждённые и предположительные связи; неполный граф не выдавать за отсутствие зависимости.
5. Jev оценивает shortlist; при отключении/сбое сохраняется builder+retrieval fallback с явным статусом.
6. По необходимости выполнить ограниченное дополнительное чтение и новую оценку; завершить по бюджетам времени/чтений/запросов, не делать бесконечную агентную разведку.
7. Собрать и перепроверить ContextBundle. Deferred candidates сохраняются для продолжения, без повторного сканирования всего дерева.

Задачи без конкретных наблюдений получают needs_evidence или обзорный пакет с открытыми вопросами. Первый read-only tool не запускает весь набор тестов, чтобы угадать задачу.

## 8. Переиспользование Jev

Выделить из пилотного клиента переиспользуемый путь типизированного state/questions и валидации ответов, сохраняя старые test-selection сценарии и проверки. Переиспользовать конфигурацию endpoint/model/credential, HTTP pool/TLS/proxy/no-redirect, ограничение тела, timeout/no blind retry, usage/cost/unknown outcome trace. Не переписывать транспорт второй раз и не использовать старые prompts выбора теста для выбора файлов.

State: полный task, ограниченные реальные project facts, candidate cards с явно видимыми IDs/paths, сигнатуры/докстринги/нужные фрагменты, связи и основание отбора, известные gaps. Несколько независимых Noul/Score для relevance/contract/test/support role; Choice — для следующего разрешённого действия. Раскрытие зависит от свежих прочитанных фактов, поэтому второй зависимый шаг — новый запрос. Сам по себе Noul не доказывает полноту пакета, а confidence не является вероятностью успешной правки.

Jev не генерирует пути/команды. Код проверяет ID, snapshot, admission и бюджет. Недостаточное состояние означает expand/uncertain, а не вынужденный отказ от файла. Подтверждённые обязательные связи нельзя выбрасывать только из-за низкой оценки Jev. Пороги фиксируются после offline qualification, не подгоняются внутри серии.

Jev остаётся на OpenRouter. Эмбеддинги и Jev включаются независимо: builder only / builder+embedding / builder+Jev / full pipeline. Первоначально проверяется одна существующая feature-enabled сборка; техническое имя feature не должно связывать runtime-включение двух сервисов.

## 9. Интерфейс и доставка

Внутренняя функция prepare_task_context(task, token_budget, cancellation) -> ContextBundle. Scope берётся из действующего binding, а не создаётся строкой пути в model prompt.

Реализован публичный `ide.prepare`: после `ide.start` один вызов с задачей возвращает
один текстовый пакет. Каталог содержит 11 инструментов; snapshots экспортируются из бинарника.
Нет continuation, обязательного inspect или скрытого опроса со стороны основного агента.
При нехватке бюджета возвращается `partial` с явными пропусками. Jev может запросить
раскрытие кандидата: IDE читает его целиком под прежними ограничениями чтения; если
целая единица не помещается, её пропуск не маскируется статусом complete.
`complete` означает доставку выбранных обязательных единиц, а не доказательство,
что произвольная задача исчерпывающе локализована.

Использовать существующий авторизованный source-read/response/outbox путь. Indexing и чтение Jev не создают main-agent read receipts. Только фактически доставленные главному агенту байты подтверждают его чтение; stale source и смена generation отменяют подготовленное решение.

Предварительный бюджет считает существующая token_estimate. Для строгого model budget нужен подходящий tokenizer; если его нет, выдавать estimated accounting и запас, не гарантировать fit. Бюджет включает task/instructions/envelope и резерв ответа, не только исходники. Oversize показывает omitted/gaps; task не обрезается молча.

## 10. Измерения и проверки

Offline corpus: локальная правка, межмодульная задача, монолит, разные языки, русский task/английский код, неопределённая задача, rename/delete, новый незакоммиченный файл. Known required sources размечает оценщик; diff решения не единственный эталон. Hidden tests/healthy reference/разметка не доступны retriever/Jev.

Проверки без inference: стабильные IDs/диапазоны, coverage/truncation, cache invalidation, deleted/stale sources, отказ доступа, отключение backend без чтения ключей, malformed vectors/IDs/429/timeout/cancellation, deterministic fake embeddings, budgets и отсутствие ложных read receipts. Проверять application-level wiring, не только функции, повторяющие реализацию.

Retrieval metrics: recall обязательных файлов/символов при фиксированном token budget, нерелевантные токены, потерянные зависимости, доля needs_evidence, время cold index/incremental update/warm query. Полноту неизвестного проекта не выражать выдуманным процентом.

Итоговые metrics: независимое качество исправления и регрессии, число поисков/чтений основного агента, end-to-end time, main/embedding/Jev tokens, известные и неизвестные расходы, CPU/RAM и отмена. Сравнивать одинаковые задачи/снимки/бюджеты; Sol отдельно от Luna. Индексацию и её амортизацию не скрывать из стоимости.

Порядок абляций: builder+точный поиск → +embeddings → +Jev; отдельно проверить Jev без embeddings, если это нужно для объяснения эффекта. Кандидат, теряющий необходимые источники или качество, не продвигать ради меньшего packet. Небольшой фиксированный набор задач для разработки и отдельные отложенные случаи для проверки переобучения.

## 11. Последовательность внедрения

1. Зафиксировать typed contracts и offline корпус/метрики. Проверка: требования и эталоны изолированы от рабочего поиска.
2. Расширить builder структурированными source records и coverage. Проверка: прежние CLI/output контракты сохранены, raw ranges соответствуют исходникам.
3. Сделать локальный индекс и точный retrieval с готовым ContextBundle без моделей. Проверка: create/edit/delete/rename и реальные packet contents.
4. Подключить API embeddings, затем local adapter того же контракта. Проверка: fixture transport и один контролируемый реальный smoke после выбора модели/лимита расходов; одинаковая семантика query/document.
5. Квалифицировать широкий отбор offline. Проверка: recall при одинаковом бюджете; embeddings не ухудшают прямые совпадения.
6. Выделить общий Jev client и внедрить semantic selection/expand. Проверка: полный state виден в приватном trace, корректный mapping IDs, offline refusals и абляция.
7. Подключить публичный facade/доставку и финальные обязательные gates на едином кандидате. Проверка: source receipts, свежесть, остановка, каталог инструментов, прежние сценарии.
8. Один согласованный сравнительный запуск Sol/Luna на фиксированных задачах; анализ, малый исправляющий шаг, повтор только по установленной причине.

После промежуточных изменений — затронутые проверки. Полный длительный gate — на готовом интегрированном кандидате, не после каждого мелкого исправления. Без публикации, установки IDE, push или merge в main.

## 12. Решения, оставшиеся перед реальными запросами

- Точная embedding-модель и размерность после оценки RU/code retrieval и расчёта стоимости первого индекса.
- Ограничение расходов на построение индекса и один запрос; отсутствие установленного лимита не означает неограниченный бюджет.
- Локальный backend/model/runtime выбирается отдельно; интерфейс предусматривается сейчас, но установка не выполняется автоматически.
- Финальное имя/контракт MCP-инструмента фиксируется перед изменением каталога.

## Фоновая индексация и предоценка

`ide.start` с `task_context.indexing.enabled=true` запускает один управляемый
индексатор. Он реагирует на подтверждённые правки и периодически сверяет внешние
изменения. `ide.stop` отменяет и дожидается его работы. Поиск `ide.prepare` читает
опубликованный SQLite-снимок, не обходит дерево и не отправляет исходники на embeddings.
Первая API-индексация требует `initial_allowed` после предоценки; по умолчанию она выключена.

Фрагменты кешируются по точному входному тексту, включая относительный путь.
Переименование меняет этот текст и может потребовать новые векторы. Неизменные
фрагменты не отправляются повторно. Неполный файл не публикуется; старые версии,
не совпадающие с текущими хешами, не выдаются. Для скриптов, конфигов и документации
без парсера используется ограниченное UTF-8-чтение. Бинарные/неподдерживаемые файлы,
файлы ключей и env-контейнеры не отправляются. Исключения и лимиты отражены в оценке.

Операторская предоценка (без клиентов, ключей и сети):

```sh
cargo run --offline --locked --features jev-pilot --example project_index -- \
  ROOT MODELS_JSON --estimate USD_PER_MILLION
```

Явное выполнение после оценки, с пределом передаваемого текста:

```sh
cargo run --offline --locked --features jev-pilot --example project_index -- \
  ROOT MODELS_JSON --index USD_PER_MILLION MAX_INPUT_BYTES
```

В отчёте разделены оценочные токены, измеренное время, фактические ответы API,
повторное использование кеша и неизвестный расход. Неполный проход даёт ненулевой
exit code. Один индекс держит единственного писателя; читатели используют WAL-снимки.

Неизвестный сетевой исход резервирует каждый затронутый фрагмент: смена размера
пакетов не вызывает повторную отправку. Подтверждённый ответ восстанавливает векторы
без оплаты. Отмена до durable before-send освобождает неотправленный резерв.
Для явного повтора неизвестного исхода оператор останавливает IDE и отдельно
принимает риск повторного списания. Команда ниже сама не отправляет HTTP и сохраняет
старые журналы под именами `*.operator-retry-*.json`; после неё нужны новая оценка
и явный запуск либо новая разрешённая активация:

```sh
cargo run --offline --locked --features jev-pilot --example project_index -- \
  ROOT MODELS_JSON --release-unresolved --accept-possible-duplicate-charge
```

Это операторская процедура, а не разрешённое автоматическое действие основного агента.
